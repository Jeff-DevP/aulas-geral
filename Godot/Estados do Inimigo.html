Estados do inimigo

Seu inimigo já faz duas coisas: espera e persegue. Se você acrescentar uma terceira, como ficar atordoado, o código começa a se embolar com um monte de if. Esta aula mostra como organizar isso com um enum e um match, e usa o resultado para fazer o inimigo parar quando o Player pega uma moeda.

Parte 1

O problema: variáveis demais para a mesma pergunta

A pergunta é sempre uma só: "o que o inimigo está fazendo agora?". Um jeito comum de responder é com uma variável true/false para cada coisa. Antes de ver a solução, tente adivinhar.

Se o inimigo usa 3 variáveis true/false (parado, perseguindo, atordoado), quantas combinações possíveis existem? E quantas fazem sentido, sendo que ele só pode estar em uma coisa por vez?

Mexa nas três caixas e veja o que o código teria que lidar:

Com enum, só estes valores existem

enum Estado { PARADO, PERSEGUINDO, ATORDOADO }

var estado := Estado.PARADO

Uma variável, três valores possíveis, nenhuma combinação inválida. Para estar em dois estados ao mesmo tempo, o código nem compila a ideia: a variável só guarda um valor.

Parte 2

O mapa de estados

Uma máquina de estados é só isto: uma lista de estados possíveis, o que acontece em cada um, e as condições que levam de um a outro. Desenhar o mapa antes de escrever evita esquecer uma saída. Clique em cada estado.

Em GDScript, a ferramenta para "faça uma coisa diferente para cada valor" é o match. Ele compara o valor com cada padrão, de cima para baixo. Quando um combina, só aquele bloco roda, e o programa continua depois do match. O padrão _ combina com qualquer valor e serve para "todos os outros".

Parte 3

Ao vivo: o que acontece quando pega a moeda?

O inimigo está no estado PERSEGUINDO e o Player coleta uma moeda. O código chama atordoar() em todos os inimigos. O que você acha que acontece depois que o atordoamento termina?

Estado: PARADODistância: —Acertos: 0

O Player anda sozinho em círculo. Clique na área e use as setas ou WASD para assumir, ou use o botão para simular a moeda.

    O inimigo, passo a passo

    Mantenha o que você já tem no _ready() (como a animação de nascer, se fez) e o _on_body_entered que emite acertou. O que muda está abaixo.

    extends Area2D

signal acertou

enum Estado { PARADO, PERSEGUINDO, ATORDOADO }

@export var speed := 90.0
@export var raio := 200.0
@export var tempo_atordoado := 1.5

var estado := Estado.PARADO
var tempo_restante := 0.0
var alvo: Node2D

func _ready():
	add_to_group("inimigos")
	alvo = get_tree().get_first_node_in_group("jogador")

func _process(delta):
	if alvo == null:
		return
	var distancia := global_position.distance_to(alvo.global_position)
	match estado:
		Estado.PARADO:
			if distancia < raio:
				mudar_estado(Estado.PERSEGUINDO)
		Estado.PERSEGUINDO:
			if distancia > raio:
				mudar_estado(Estado.PARADO)
			else:
				global_position += global_position.direction_to(alvo.global_position) * speed * delta
		Estado.ATORDOADO:
			tempo_restante -= delta
			if tempo_restante <= 0.0:
				mudar_estado(Estado.PARADO)

func mudar_estado(novo):
	estado = novo
	match novo:
		Estado.ATORDOADO:
			modulate = Color.GRAY
		_:
			modulate = Color.WHITE

func atordoar():
	tempo_restante = tempo_atordoado
	mudar_estado(Estado.ATORDOADO)

func _on_body_entered(body):
	if body.is_in_group("jogador"):
		acertou.emit()
    1. enum: cria o dicionário de nomes Estado.PARADO, Estado.PERSEGUINDO e Estado.ATORDOADO. Os valores internos são 0, 1 e 2, mas você nunca precisa usá-los.
    2. add_to_group("inimigos"): coloca este inimigo no grupo que o Level vai chamar. Sem isso, o call_group não o encontra.
    3. if alvo == null: return: protege o resto do _process caso o Player ainda não exista.
    4. match estado: roda só o bloco do estado atual. A cada quadro, cada estado olha a situação e decide se muda de estado.
    5. PERSEGUINDO: se o Player saiu do raio, volta a PARADO. Senão, anda na direção dele, como na aula 11.
    6. ATORDOADO: desconta o tempo restante a cada quadro. Quando chega a zero, volta a PARADO, e no quadro seguinte PARADO decide se já vai perseguir de novo.
    7. mudar_estado: único lugar que troca o estado e aplica a cor. Tudo que passa por ela já ganha o cinza ou o branco corretos.
    8. atordoar: não faz nada além de reiniciar o tempo e trocar de estado. Chamá-la de novo durante o atordoamento só reinicia a contagem.

    Uma decisão de design que ficou de fora de propósito: um inimigo atordoado ainda acerta o Player se ele esbarrar. Isso é o _on_body_entered sem nenhuma checagem de estado. Veja o desafio 3 para mudar isso.

    Fazendo no seu projeto

    Quatro passos. Marque cada um quando terminar.

    1. Atualize o inimigo.gd

      Troque o conteúdo pelo código da parte 4 e mantenha as suas linhas extras no _ready(), se tiver. Rode com F5 antes de seguir: o inimigo deve esperar parado e perseguir só quando o Player entrar no raio. Se o seu @export var raio já existia, o valor que está no Inspetor continua valendo.

    2. Atordoe os inimigos ao coletar moeda

      No level.gd, acrescente uma linha na função que soma os pontos:

      func _on_moeda_coletada(valor):
	pontos += valor
	label.text = "Pontos: %d" % pontos
	get_tree().call_group("inimigos", "atordoar")

      Adapte o resto da função ao que você já tem. A linha nova é só a última.

    3. Teste

      Deixe um inimigo perto de você perseguindo e colete uma moeda. Ele deve ficar cinza e parar por 1,5 s. Depois volta ao normal e, se você ainda estiver no raio, volta a perseguir. Mude tempo_atordoado no Inspetor, com o inimigo selecionado, e teste de novo.

    4. Responda antes de seguir

      Rode o jogo e tente prever a resposta antes de testar: se você coletar duas moedas seguidas, com 0,5 s entre elas, o inimigo fica atordoado por 3 s, por 2 s ou por 1,5 s? Anote o palpite, teste, e depois leia o item 8 das notas da parte 4.

    Parte 7

    Checagem do que você entendeu

    Um estado é "o que o objeto está fazendo agora", e ele só pode estar em um por vez. O enum garante isso: a variável guarda um único valor, entre os que você listou. Com vários true/false, existem combinações que não fazem sentido (parado e perseguindo ao mesmo tempo) e o código precisa se defender de todas.

    Desafios (dica primeiro)

    Desafio 1: mostrar o nome do estado em um Label

    Coloque um Label filho do inimigo que mostre "PARADO", "PERSEGUINDO" ou "ATORDOADO", atualizado a cada troca.

    Um enum nomeado é um dicionário. Que método de dicionário devolve a lista de nomes? E em qual função você garante que toda troca de estado passa por um único lugar?

    func mudar_estado(novo):
	estado = novo
	$Label.text = Estado.keys()[novo]
	match novo:
		Estado.ATORDOADO:
			modulate = Color.GRAY
		_:
			modulate = Color.WHITE

    O keys() devolve os nomes na ordem em que foram escritos no enum, e o valor de cada estado (0, 1, 2) é o índice dessa lista.

    Desafio 2: estado ALERTA antes de perseguir

    Quando o Player entra no raio, o inimigo fica 0,5 s em um estado ALERTA (parado) antes de começar a perseguir, como um tempo de reação.

    É o mesmo padrão do ATORDOADO: um estado novo no enum, um bloco novo no match que desconta tempo_restante, e quem decide ir para ele é o estado PARADO. Quem o ALERTA deve levar para o PERSEGUINDO?

    enum Estado { PARADO, ALERTA, PERSEGUINDO, ATORDOADO }

@export var tempo_alerta := 0.5

# dentro do match estado:
Estado.PARADO:
	if distancia < raio:
		tempo_restante = tempo_alerta
		mudar_estado(Estado.ALERTA)
Estado.ALERTA:
	tempo_restante -= delta
	if tempo_restante <= 0.0:
		mudar_estado(Estado.PERSEGUINDO)

    Esta versão persegue mesmo se o Player sair do raio durante o alerta, e só no estado seguinte decide voltar a PARADO. Dá para refinar isso depois.

    Desafio 3: o inimigo atordoado não pode acertar

    Faça o inimigo atordoado ficar inofensivo. Cuidado: tem uma pegadinha.

    Uma checagem de estado dentro do _on_body_entered resolve o caso fácil. Agora pense em quando esse sinal dispara: só na entrada. E se o Player já estiver encostado no inimigo quando o atordoamento terminar? Procure na ajuda do editor (tecla F1, classe Area2D) se existe algo para listar o que já está sobreposto. Eu ainda não conferi o nome exato na documentação, então me conte o que você encontrou e eu confirmo antes de montar a solução.

    Este desafio não tem solução pronta de propósito: é para você pesquisar e me trazer a sua tentativa.

    Resumo em três linhas

    • Um estado é o que o objeto está fazendo agora, e o enum garante um valor só por vez.
    • O match roda o bloco do estado atual, e cada bloco decide se troca de estado.
    • Concentrar a troca em mudar_estado() deixa os efeitos de entrada (como a cor) em um lugar só.
